# 自动发布失败与源码包完整性

## 问题

PowerShell 默认的遇错停止行为不一定将原生命令的非零退出码转为异常。若 GitHub CLI 上传失败后仍继续执行公开命令，可能发布缺少附件的 Release。直接创建公开 Release 也会在上传中途对外暴露不完整版本。

现有源码打包脚本按白名单复制目录，不包含 `.github`；添加 CI 后若不更新白名单，源码附件将丢失自动发布配置。

## 解决

- 使用 `gh release create --draft` 创建草稿并上传五个附件，明确检查 `$LASTEXITCODE`；仅成功后执行 `gh release edit --draft=false`，同样检查退出码。
- 对 Python 测试的退出码也显式检查；任一前置步骤失败，后续上传、公开步骤不运行。
- 上传失败可能遗留部分附件的草稿。记录恢复方式：确认未公开后删除本次失败草稿，再重跑；已公开版本不覆盖。公开请求发生网络故障时，以 GitHub 页面实际状态为准。
- 将 `.github` 加入源码复制白名单；在临时副本中构建、打包，检查源码 ZIP 中的工作流、校验脚本、测试和文档，避免覆盖 `dist` 既有发布包。

## 验证

actionlint 1.7.7 检查工作流通过；15 项隔离 tag 检查和 16 项路径模型检查通过；隔离构建、版本/PE/包内 DLL/哈希校验及新增源码文件检查通过。GitHub 上传及权限仍需首次新版本 tag 的真实运行验证。
